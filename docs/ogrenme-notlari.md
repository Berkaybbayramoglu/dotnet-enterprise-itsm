## Faz 8: Dashboard, Raporlama, Arama & Filtreleme, Knowledge Base
**Kavram:** Entity Framework Core In-Memory Testleri ve `IQueryable` Davranış Farklılıkları
**Basit Açıklama:** Unit testlerde kullanılan In-Memory provider, SQL'e dönüştürülen LINQ sorgularını (örneğin `.ToLower().Contains()`) client-side (bellekte) çalıştırır. Eğer veritabanında "required" (zorunlu) ilişkiler tanımlandıysa (örneğin foreign key olan bir alan nullable değilse), EF Core bu ilişkiyi `INNER JOIN` olarak algılar. Test verisi oluştururken ilişkili entity'leri (Category, Type, Priority) DB'ye eklemezseniz, In-Memory testlerde dahi `Include` veya Navigation Property sorguları (INNER JOIN nedeniyle) ana kaydı getirmez ve testler gizlice başarısız olur.
**Projede Nerede:** `ReportServiceTests.cs` (ExportTicketsToCsvAsync) ve `TicketService.cs` (SearchTicketsAsync)
**Mentor Sorarsa Cevabın:** "Raporlama servislerini test ederken In-Memory veritabanının required (zorunlu) foreign key'ler için INNER JOIN mantığında çalıştığını fark ettim. Test ortamında Ticket oluştururken Category, Type, Priority gibi zorunlu ilişkili tabloları mock olarak doldurmadığımız için `Include` yapıldığında kayıtlar eşleşmiyor ve filtreye takılıyordu. Test verilerini (Category, Type, vb.) context'e ekleyerek bu sorunu çözdüm ve `NullReferenceException`'ları engelledim. Ayrıca frontend tarafında API entegrasyonu için Fetch API kullanarak `api.js` wrapper class'ı oluşturdum."


## Faz 8: Frontend A11y & Readability (WCAG, SonarQube)
**Kavram:** Web Accessibility (a11y), WCAG Temelleri, Semantik Butonlar ve Klavye Navigasyonu
**Basit Açıklama:** Ön yüz geliştirmelerinde tıklanabilir öğeler için (aksiyon veya JavaScript fonksiyonu çağıranlar) `<a href="#">` veya `onclick` event'ine sahip `<span>`/`<div>` gibi non-native (semantik olmayan) etiketler kullanmak erişilebilirliği ve ekran okuyucu (screen reader) deneyimini bozar. Ekran okuyucular anchor etiketlerini sayfa değişimi veya içi boş link olarak okurken, native `<button>` elementlerini doğrudan "Düğme" olarak tanır ve Space/Enter tuşlarıyla yerleşik (built-in) klavye olaylarını (keydown/keyup) yönetir. Input elementleri her zaman `<label for="id">` veya `aria-label` ile birleştirilmeli, boş başlıklar (`<h2></h2>`) DOM'da bulunmamalıdır. Ayrıca modern JavaScript'te global regex (`/g`) ile `String#replace` kullanmak yerine `String#replaceAll` kullanmak kodun okunabilirliğini artırır.
**Projede Nerede:** `wwwroot` altındaki tüm HTML dosyaları (`tickets.html`, `kb.html`, `dashboard.html`) ve `api.js` (`escapeHtml` regex kullanımı vb.)
**Mentor Sorarsa Cevabın:** "Frontend sayfalarımızda aksiyon gerçekleştiren (örneğin Logout yapan) HTML öğelerini `<a href="#">` yerine CSS ile şekillendirilmiş semantik `<button type="button">` elementleriyle değiştirdim. Böylece ekran okuyuculara ve sadece klavye kullanan kişilere (tab navigation) tam destek sağladık. Form elemanlarında erişilebilirlik (aria-label) geliştirmeleri yaptım ve JavaScript kodlarımızdaki karmaşık regex değiş tokuşlarını modern `replaceAll` metoduna geçirerek 'Code Smell' hatalarını temizledim."

## Faz 8: Konfigürasyon Senkronizasyonu (Single Source of Truth)
**Kavram:** Config Drift (Yapılandırma Kayması), Single Source of Truth (Tek Kaynak Doğruluğu) ve Port Sözleşmeleri
**Basit Açıklama:** Büyük projelerde veritabanı bağlantı adresi (connection string) veya API URL'i gibi kritik yapılandırmalar birden fazla yerde hardcode edilirse, zamanla birisi güncellendiğinde diğeri unutulur; buna *Config Drift* denir. `ItsToolDbContextFactory`'nin design-time connection string'i manuel yazıldığında API tarafındaki `appsettings.json`'dan farklı kalabilir. Bu yüzden tüm veriler tek bir kaynaktan (`appsettings.json`) beslenmelidir (Single Source of Truth). Ayrıca Web projelerinin Backend API'ye istek yaparken kullandığı port, Backend'in `launchSettings.json` içindeki `applicationUrl` ayarıyla ve `appsettings.json` içindeki `Cors:AllowedOrigins` listesiyle kesinlikle eşleşmelidir.
**Projede Nerede:** `ItsToolDbContextFactory.cs`, `api.js`, API `appsettings.json` ve `launchSettings.json`
**Mentor Sorarsa Cevabın:** "Çalışma zamanında connection string uyuşmazlığından ve port sorunlarından kaçınmak için `ItsToolDbContextFactory` sınıfını refactor ettim; artık connection string'i hardcoded olarak değil, dinamik olarak `ItsTool.API` içindeki `appsettings.json` dosyasından okuyor. Ayrıca frontend API istek URL'ini API'nin `launchSettings.json` portuyla tam hizaladım ve CORS izinlerini doğruladım."

## Faz 8: ASP.NET Core Static Files Middleware & Routing
**Kavram:** Middleware Pipeline, `UseStaticFiles`, `UseDefaultFiles` ve Routing (Yönlendirme)
**Basit Açıklama:** ASP.NET Core uygulamasında `wwwroot` altındaki HTML/CSS/JS dosyalarını dışarı sunmak için HTTP pipeline'ında `app.UseStaticFiles()` çağırmak zorunludur. Ayrıca `http://localhost:5139/` gibi kök dizin isteklerinde otomatik olarak `index.html` sayfasının servis edilmesi için `app.UseDefaultFiles()` eklenmelidir. Bu iki middleware'in *sıralaması* çok önemlidir; `UseDefaultFiles`, URL'i `index.html` olarak rewrite (yeniden yazma) işlemi yapar ancak dosyayı servis edemez, bu yüzden **mutlaka** `UseStaticFiles`'dan önce çağrılmalıdır. Aksi halde `MapGet("/")` gibi minimal API route'ları (örneğin "Hello World" placeholder'ı) isteği yakalar ve statik dosyaların gösterilmesini engeller.
**Projede Nerede:** `ItsTool.Web/Program.cs`
**Mentor Sorarsa Cevabın:** "Web projemizde `wwwroot` içindeki frontend kodlarımızın tarayıcıdan açılmamasının sebebi, ASP.NET Core'un varsayılan olarak statik dosya sunumuna kapalı olması ve kök dizinin API endpoint'ine (Hello World) yönlendirilmiş olmasıydı. `Program.cs` dosyasına, URL'i `index.html`'e yönlendirmesi için `app.UseDefaultFiles()` ve ardından bu dosyayı fiziksel olarak sunması için `app.UseStaticFiles()` middleware'lerini doğru sırayla ekleyerek sorunu çözdüm."

## Faz 8: HTML5 Validation ve Backend Login Sözleşmesi
**Kavram:** Client-Side Validation vs Backend Sözleşmesi, "Username or Email" Pattern'i
**Basit Açıklama:** HTML5'teki `type="email"` özelliği, form submit edilmeden önce tarayıcının '@' işareti gibi email formatlarını zorlamasını sağlar (Client-Side Validation). Eğer backend sistemi (AuthService) kullanıcının hem "Username" (örn: admin) hem de "Email" ile giriş yapmasına izin verecek şekilde tasarlandıysa, frontend'deki katı `type="email"` kısıtlaması, doğru bir Username girildiğinde bile isteğin API'ye gitmesini engeller. Bu uyuşmazlığı çözmek için frontend'de input `type="text"` (veya tel, vs.) olarak esnetilir ve `autocomplete="username"` ile tarayıcıya ipucu verilir. Backend'de ise veritabanı sorgusu `Username == input OR Email == input` şeklinde genişletilir.
**Projede Nerede:** `login.html` ve `AuthService.cs` (`LoginAsync` metodu).
**Mentor Sorarsa Cevabın:** "Login formunda sadece e-posta değil, 'admin' gibi kullanıcı adlarıyla da giriş yapılabilmesi gerekiyordu. Ancak HTML'deki `type="email"` kısıtlaması yüzünden 'admin' yazınca tarayıcı '@' beklediği için formu göndermiyordu. HTML'deki input tipini `text` olarak güncelledim ve backend `AuthService`'i hem Username hem de Email ile eşleşme (case-insensitive) yapacak şekilde refactor ettim."

## Faz 8: Dashboard Frontend-Backend Veri Kontratı
**Kavram:** Frontend-Backend Sözleşmesi (Contract), DTO Naming Conventions ve Defensive Rendering
**Basit Açıklama:** Backend tarafında C# ile oluşturulan DTO'lardaki property isimleri (örneğin `SlaBreachedTickets`), JSON olarak serialize edildiğinde varsayılan olarak camelCase yapısına (`slaBreachedTickets`) bürünür. Frontend JavaScript kodu, backend API'den gelen veriyi render ederken hatalı özellik (property) isimleri kullanırsa (örneğin `slaBreachedCount`) değer `undefined` döner ve HTML içinde hatalı görünür. JavaScript tarafında veriyi ekrana basarken `?? 0` (Nullish Coalescing Operator) gibi tekniklerle varsayılan (fallback) değerler vermek, veri gelmediğinde arayüzün bozulmasını engeller (Defensive Rendering).
**Projede Nerede:** `DashboardOverviewDto.cs`, `dashboard.html`
**Mentor Sorarsa Cevabın:** "Dashboard arayüzünde bazı metriklerin 'undefined' yazdığını tespit ettik. İncelediğimde C# tarafındaki DTO'nun (DashboardOverviewDto) `SlaBreachedTickets` isimli property döndürdüğünü, ancak JS tarafında bunun `slaBreachedCount` olarak okunduğunu gördüm. Tek doğru kaynağın (Single Source of Truth) backend DTO'su olması prensibiyle JS tarafını DTO isimlerine uyacak şekilde (camelCase haliyle) güncelledim. Ayrıca verilerin `null` gelme ihtimaline karşı defensive rendering uygulayarak `(deger ?? 0)` fallback yapısını ekledim."

## Faz 9: Gelişmiş Dinamik Yapılandırma & Rules Engine Deseni
**Kavram:** Rules Engine (Condition-Action) Deseni, Config-Driven Form Render, Saved Filter Serialization, Event-Driven Notification Fan-out.
**Basit Açıklama:** Gelişmiş dinamik konfigürasyonlarda (örn. Bilet Atama Kuralları) sisteme hardcode edilmiş bir atama mantığı yazmak yerine, kuralların bir tabloda (AssignmentRules) tutulup çalışma zamanında (Runtime) değerlendirilmesi *Rules Engine* desenidir. Böylece kodu değiştirmeden yeni kurallar eklenebilir. Benzer şekilde, bilet formları da `FormFieldPlacement` üzerinden "Config-Driven" olarak JSON aracılığıyla render edilir. Event-Driven bildirim üretiminde ise `NotificationDispatcher`, bir olay (örn: ticket.created) gerçekleştiğinde abone olan kuralları tarayarak "Fan-out" (çoğaltma) yapar ve kişilere özel bildirim yaratır; aynı kişiye aynı olay için bir daha bildirim atılmasını engellemek de (Duplicate Prevention) önemli bir tasarım kararıdır.
**Projede Nerede:** `AssignmentEngine.cs`, `NotificationDispatcher.cs`, `SavedFilterController.cs`, `ticket-create.html` ve `api.js`.
**Mentor Sorarsa Cevabın:** "Uygulamamızı tamamen 'Configuration-Driven' yapmak için, bilet açıldığında kimlere atanacağına karar veren bir *Assignment Rules Engine* yazdım ve bilet akışına entegre ettim. Ayrıca *Notification Dispatcher* pattern'i uygulayarak biletteki tüm önemli state değişikliklerini (created, assigned, comment_added) dinleyen ve aktif kurallara göre çoklu kişilere spam/duplicate olmadan bildirim atan bir mekanizma kurdum. Kullanıcıların arama filtrelerini kaydetmeleri için JSON serialization tekniğini (SavedFilter) kullandım ve son olarak bilet formlarının tamamen konfigürasyon tabanlı olarak dinamik şekilde render edildiği UI altyapısını oluşturdum."

## Faz 12: SonarQube Temizliği (Pass 3) - C# Optimizasyonları
**Kavram:** Member Hiding vs Inheritance, NRT (Nullable Reference Types) Guard desenleri, Culture-Independent String Comparison (OrdinalIgnoreCase) ve DI Temizliği.
**Basit Açıklama:** C#'ta bir base class'tan (`BaseEntity`) miras gelen property (`IsActive`), derived class'ta tekrar tanımlandığında (member hiding) `new` keyword kullanılmamışsa derleyici uyarısı verir. Bunu önlemek için derived class'taki (örneğin `WebhookSubscription` ve `AssignmentRule`) gereksiz property tanımları kaldırıldı; bu durum veritabanı şemasını değiştirmediği için migration gerektirmedi. Arama ve filtrelemelerde kullanılan `ToLower()` metotları culture-specific hatalara yol açabileceği için yerine `Equals(..., StringComparison.OrdinalIgnoreCase)` kullanımı denenmişti; ancak Entity Framework Core'da PostgreSQL (Npgsql) provider'ı bu overload'u desteklemediği için (LINQ expression could not be translated) çalışma zamanı (runtime) hatalarına sebep olur. EF Core In-Memory testleri istemci tarafında çalıştığı için bu hatayı gizler. Bu yüzden veritabanı sorgularında (`FirstOrDefaultAsync` veya `Where` içinde) `.ToLower() == value.ToLower()` pattern'ine geri dönülmüştür. Controller katmanında `CreatedBy` gibi nullable veriler `?? "system"` gibi guard pattern'leri ile korunarak güvenli hale getirildi. Gereksiz null-forgiving (`!`) operatörleri temizlendi ve performansı artırmak için listeler üzerinde `.Any()` yerine `.Count > 0` (veya `Count == 0`) kullanıldı. Son olarak, DI (Dependency Injection) container'a eklenip constructor'da alınan ancak hiç kullanılmayan bağımlılıklar (`_ticketService` gibi) koda gereksiz yük ve memory allocation bindirdiği için kaldırıldı ve test mock'ları da bu değişime uyarlandı.
**Projede Nerede:** `WebhookSubscription.cs`, `AssignmentRule.cs`, `AuthService.cs`, `EmailIngestionService.cs`, `KnowledgeBaseService.cs`, `ReportService.cs`, `AuditLogController.cs`, `DashboardService.cs`, `NotificationDispatcher.cs`
**Mentor Sorarsa Cevabın:** "SonarQube'ün backend'de işaret ettiği gizli uyarıları çözdüm. Miras alınan property'lerin yeniden tanımlanması (member hiding) kod karmaşasına sebep oluyordu, base sınıfa güvendim. E-posta ve kullanıcı adı eşleştirmelerinde kültürden bağımsız (OrdinalIgnoreCase) aramalar yaparak ReDoS veya bug riskini azalttım. En önemli performans iyileştirmesi olarak, kullanılmayan DI servislerini temizledim; çünkü kullanmadığın bağımlılığı constructor'da istemek, instance üretme maliyetini artırır ve testleri gereksiz karmaşıklaştırır."

## Faz 12: SonarQube Temizliği (Pass 4) - Null Dereference & Contrast & Top-Level Await
**Kavram:** NRT Guard vs Null-Forgiving, WCAG Kontrast (4.5:1), Module Script ve Top-Level Await
**Basit Açıklama:** C# 8+ Nullable Reference Types (NRT) özelliğinde bir referansın sonuna `!` (Null-Forgiving operator) eklemek derleyiciye "bunun null gelmeyeceğine ben kefilim, uyarıyı yut" demek anlamına gelir; ancak değer çalışma zamanında (runtime) gerçekten `null` gelirse `NullReferenceException` fırlatılır. Bunun yerine *Guard Pattern* uygulanıp değişkenin önce `null` olup olmadığı `?.` veya `??` (fallback) operatörleriyle "kanıtlanmalıdır". `DashboardService` içinde bu yüzden `!` kaldırılıp fallback atamalar (ternary operator veya null-conditional) eklenmiştir. 
Frontend'de Web Content Accessibility Guidelines (WCAG) AA standardı uyarınca, açık renkli arka planlar üzerindeki metin veya buton renklerinin kontrast (zıtlık) oranı en az `4.5:1` olmalıdır (Örn: `#0056b3` rengi beyaz yazıyla açık zeminlerde bu oranı karşılamadığı için `#004085` gibi daha koyu tonlara çekilmiştir).
Son olarak `tickets.html` sayfasındaki JavaScript, top-level `await` kullanarak asenkron filtre ve tablo yüklemesini sağladığı için `<script type="module">` olarak sarmalanmış; böylece HTML sayfasındaki inline metot çağrıları (`onclick="search()"`) izolasyondan çıkabilmek adına `window.search = search;` yöntemiyle global scope'a aktarılmıştır. Bu sayede tüm frontend modül standardına uyumlu (ECMAScript Module) hale getirilmiştir.
**Projede Nerede:** `DashboardService.cs`, tüm `wwwroot/*.html` (özellikle buton arkaplanları), `tickets.html`.
**Mentor Sorarsa Cevabın:** "Null-Forgiving operatörü hatayı sadece derleme zamanında gizlediği için, çalışma zamanında patlama (crash) riskini önlemek adına verileri if veya ternary kontrollerle sağlama aldım. Arayüzde WCAG erişilebilirlik gereksinimlerini karşılamak amacıyla renk kontrast oranlarını artırıp butonları daha okunaklı yaptım. Aynı zamanda eski sayfalardaki top-level await kullanımını (tickets.html) module script standardına çekerek tüm UI mimarisini güncel ES6 standardında birleştirdim."

**Basit Açıklama:** Uygulamanın amatör görünen (Basic HTML/CSS ve Bootstrap) arayüzünü modern bir web uygulaması (SPA hissiyatlı) haline getirmek için "App Shell" mimarisi uygulandı. Tarayıcının çirkin ve senkron engelleyici `alert()` veya `confirm()` fonksiyonları yerine, asenkron ve şık davranan `showToast()` gibi özel UI Helper metotları kullanılarak UX profesyonelleştirildi.
**Projede Nerede:** `wwwroot` altındaki tüm HTML dosyaları (login, tickets, dashboard, ticket-detail vb.), `css/design-system.css`, `js/ui.js`
**Mentor Sorarsa Cevabın:** "Frontend yapısını dış bağımlılıklardan (Bootstrap gibi) tamamen kurtarıp, sıfırdan token tabanlı bir 'Vanilla CSS Design System' kurdum. Jira ve ClickUp gibi sektör standartlarından ilham alarak 'App Shell' mimarisini uyguladım; böylece kullanıcı sayfalar arası gezerken tutarlı bir deneyim (sidebar/topbar) yaşıyor. Kodun bakımını kolaylaştırmak için JavaScript tarafında `ui.js` üzerinden `showToast` gibi merkezi helper fonksiyonları kullandım ve tarayıcının standart (alert) diyaloglarını terk ettim."

## Faz 12: SonarQube Temizliği (Pass 5) - Final Taraması Kapanışları
**Kavram:** Culture-Independent String Comparison (Türkçe "i" Problemi), NRT Guard Deseni Tekrarı, Accessibility (Boş Başlıklar) ve Regex `replaceAll`.
**Basit Açıklama:** C# tarafında arama, e-posta ve kullanıcı adı eşleştirmelerinde kültür bağımsız `StringComparison.OrdinalIgnoreCase` kullanmak kritik bir güvenlik ve mantık gereksinimidir. Örneğin Türkçe klavyede büyük "i" harfi "İ" iken İngilizce'de "I"dır. Sadece `.ToLower()` kullanırsak, sunucunun çalıştığı bölge ayarlarına göre eşleşme hataları yaşanır (The Turkish "I" problem). Bu yüzden `OrdinalIgnoreCase` kullanılarak ASCII tablosu üzerinden doğrudan byte eşleşmesi yapılmalıdır (Not: Bu değişiklik In-Memory testlerde yeşil verir ancak EF Core PostgreSQL gibi bazı DB provider'larında IQueryable expression tree'si içerisinde çeviri hatası fırlatabilir; bu durumda `EF.Functions.ILike` veya istemci taraflı değerlendirme gibi yöntemlerle çözülmesi gerekir). 
Diğer bir konu olan NRT Guard deseni (`?.` ve `??` operatörleri), bir referansın çalışma zamanında `null` olma ihtimaline karşı zorunlu olarak uygulanmıştır. Ancak unutulmamalıdır ki `?.` null-conditional operatörü EF Core IQueryable (Expression Tree) içinde CS8072 hatasına sebep olur; bu yüzden `x != null ? x.Value : "fallback"` şeklinde ternary IF operatörü ile yazılmalıdır.
Frontend tarafında ise ekran okuyucuların (screen readers) kafasını karıştırmamak adına içi boş `<h1...h6>` başlık etiketleri bırakılmamış ("Loading..." gibi varsayılan metinler eklenmiş) ve JavaScript tarafındaki riskli `/g` regex replace işlemleri, daha modern, net ve performanslı olan `replaceAll()` metoduna dönüştürülmüştür.
**Projede Nerede:** `AuthService.cs`, `KnowledgeBaseService.cs`, `TicketService.cs`, `ReportService.cs`, `EmailIngestionService.cs`, `DashboardService.cs`, `kb.html`, `ticket-detail.html`
**Mentor Sorarsa Cevabın:** "Son SonarQube bulgularını kapatırken özellikle Türkçe 'I-i' dönüştürme problemlerini aşmak için kültürden bağımsız (OrdinalIgnoreCase) string karşılaştırmalarını zorunlu hale getirdim. Arayüzde boş HTML başlıklarını doldurarak erişilebilirliği (a11y) yüzde yüz uyumlu hale getirdim ve backend tarafında null hatalarını engellemek için expression-tree dostu ternary guard yapılarını uyguladım."
## Faz 12: CSS Stacking Contexts ve Modal A11y (Erişilebilirlik)
**Kavram:** CSS Stacking Context (z-index), Fixed vs Relative Positioning, Focus Trapping ve Klavye Navigasyonu (ESC).
**Basit Açıklama:** Uygulamalardaki Modal (Popup) pencereleri genellikle ekranın geri kalanını kapatan bir "Overlay/Backdrop" tabakası ve üzerinde ortalanmış bir "Modal İçeriği"nden oluşur. `position: absolute` ile bir overlay çizmeye çalışmak viewport'un (görünür ekranın) tamamını kaplamayabilir (özellikle scroll varsa); bu yüzden overlay'ler `position: fixed; inset: 0;` (veya top/left/right/bottom: 0) şeklinde tanımlanmalıdır. `z-index` kuralının çalışması için elemanların mutlaka bir stacking context (örn: fixed, relative, absolute) içinde olması gerekir (bu projede overlay z-index: 1000, modal content z-index: 1001). 
Erişilebilirlik (A11y) açısından bir modal açıldığında, arka plandaki (sayfadaki) elemanlar "Focus Trap" (odak tuzağı) ile gizlenmeli veya modal içindeki ilk `<input>` alanına otomatik focus yapılmalıdır. Modal'ı kapatmak için sadece "X" butonuna tıklamak yetmez; kullanıcı ESC tuşuna bastığında veya backdrop (modal dışındaki karanlık alan) üzerine tıkladığında modal kapanmalı ve focus (odak), modal'ı açan asıl butona geri verilmelidir (lastActiveElement). Bu, klavye ve ekran okuyucu kullanıcıları için hayati önem taşır.
**Projede Nerede:** `css/design-system.css`, `js/ui.js` ve modal kullanan tüm HTML sayfaları (`admin-fields.html`, `rules.html`, `webhooks.html`, `kb.html`).
**Mentor Sorarsa Cevabın:** "Arayüzdeki kırık modal yapılarını düzeltirken CSS Stacking Context kurallarını derinlemesine öğrendim. Modal'ın tüm ekranı kaplaması için `position: fixed` ve `inset: 0` kullanımını uygulayıp, HTML yapısını `modal-overlay > modal` şeklinde standartlaştırdım. En önemlisi, engelli kullanıcılar veya Power User'lar için Focus Trapping (odak yakalama) mantığını kodladım; artık modallar açıldığında ilk input'a odaklanıyor, ESC veya backdrop tıklamasıyla kapanıyor ve odak, modal'ı açan butona geri dönüyor."

## Faz 12.7: 403 Stale Permission Hardening ve Auto-Seed
**Kavram:** JWT Claim Snapshot Doğası, Idempotent Seeding ve "Dev-Only Auto-Seed" Pattern'i.
**Basit Açıklama:** JWT token'lar, oluşturuldukları andaki yetkilerin (permissions) "snapshot"ını yani anlık görüntüsünü içerirler. Eğer backend'e yeni bir yetki (Permission Key) eklenirse ve bu yetki veritabanına `DataSeeder` aracılığıyla yazılıp rollere atanırsa, halihazırda elinde token bulunan admin kullanıcılar bu yeni yetkiden haberdar olamazlar ve 403 Forbidden hatası alırlar (çünkü token'larındaki claim'ler eksiktir). Çözüm olarak adminin "re-login" olması yani oturumu kapatıp açarak token'ı yenilemesi gerekir. Sistemdeki bu süreci yumuşatmak için iki strateji izlenir: Birincisi; frontend tarafında 403 hataları yakalanarak "Yetkiniz yok veya oturum bilgileri güncel değil — yeniden giriş yapmayı deneyin" şeklinde anlamlı bir hata (Graceful Degradation) verilir. İkincisi; Development (Geliştirme) ortamında bu tür yetki güncellemelerinin geliştiricileri bloke etmemesi için `appsettings.Development.json` dosyasına `"AutoSeed": true` flag'i eklenerek `Program.cs`'in başlangıcında (startup) `DataSeeder` otomatik çalıştırılır. Bu özellik kesinlikle "Dev-Only" olmalıdır; çünkü Production (Canlı) ortamda birden fazla sunucu aynı anda ayağa kalkarken `AutoSeed` yarış koşullarına (race condition) veya performans kayıplarına yol açabilir. Canlıda veritabanı migration ve seed işlemleri CI/CD pipeline'larında izole olarak yürütülür.
**Projede Nerede:** `Program.cs`, `appsettings.Development.json`, `DataSeeder.cs`, `api.js`.
**Mentor Sorarsa Cevabın:** "Sisteme yeni permission'lar (yetkiler) eklediğimizde elinde eski token bulunan kullanıcıların sürekli 403 hatası alıp kilitlenmesi sorununu iki koldan çözdüm. Geliştirme ortamında (Development) `AutoSeed` flag'i ile uygulamanın her açılışında `DataSeeder`'ı çalıştırarak veritabanının otomatik senkronize olmasını sağladım. Bu flag'in Production'da olmamasının sebebi canlıdaki multi-instance yapıda race condition'ları engellemektir. Önyüzde ise 403 hatalarını yakalayıp kullanıcıya 'Yetkiniz güncel değil, yeniden giriş yapın' mesajı vererek teşhisi kolaylaştırdım."

## Faz 12.8: 403 Kök Neden Avı - Tam Idempotent Seeder ve Permission Calculator Filtreleri
**Kavram:** Idempotent Seeding, Soft Delete Filtreleri ve EF Core LINQ Translation.
**Basit Açıklama:** Gelişmiş veritabanı işlemlerinde (Data Seeding) bir kaydın daha önceden var olup olmadığını kontrol edip eklemek tam olarak "idempotent" sayılmaz. Özellikle Role-Permission bağlarında, eğer izin (Permission) mevcut ama role atanmamışsa, basit bir "if (!permissions.Any())" veya "if (!existingKeys.Contains(key))" kontrolü yetersiz kalır. Bu durum, admin kullanıcıların gerekli yetkilere sahip olamamasına (403 Forbidden) yol açar. Bu yüzden DataSeeder tam idempotent hale getirilerek her bir yetkinin hem `Permissions` tablosunda varlığı hem de `SuperAdmin` için `RolePermissions` tablosunda atanmış olup olmadığı tek tek doğrulanıp eksikler tamamlanmalıdır. Benzer şekilde `admin` kullanıcısının `SuperAdmin` rolüne sahip olup olmadığı da `UserRoles` tablosu üzerinden kontrol edilmeli ve atama eksikse eklenmelidir.
Diğer yandan, `PermissionCalculator.cs` gibi çoklu `Join` işlemi yapan LINQ sorgularında, `BaseEntity` tabanlı "Soft Delete" mekanizması uygulanan tablolarda `!IsDeleted` kontrolü her bir varlık (Entity) için (`ur.IsDeleted`, `rp.IsDeleted`, `p.IsDeleted` vb.) eklenmek zorundadır. Eğer bu kontroller unutulursa, silinmiş (soft-deleted) bir rol veya yetki, kullanıcıya verilmiş gibi hesaplanarak yetki sızıntısına (Permission Leak) veya yanlış JWT claim'leri üretimine sebep olur.
**Projede Nerede:** `DataSeeder.cs`, `PermissionCalculator.cs`, `PermissionCalculatorTests.cs`
**Mentor Sorarsa Cevabın:** "Sistemdeki 403 authorization hatalarını debug ederken, DataSeeder'ın tam idempotent olmadığını, yani eksik rol-yetki bağlarını tamamlamadığını fark ettim. Bunu çözüp tam idempotent hale getirdim. Ayrıca PermissionCalculator üzerinde soft-delete (IsDeleted) kontrollerinin eksik olduğunu gördüm ve tüm LINQ sorgularını 'IsDeleted == false' kontrolleri ile güçlendirerek yetki sızıntılarını engelledim. Bu düzeltmeleri de özel Unit Test'ler yazarak koruma altına aldım."

## Faz 12.9: 404 Lookup Optimizasyonu, Modal Dayanıklılığı ve Enum Map Sözleşmesi
**Kavram:** Backend Route Optimizasyonu, CSS Stacking Tabanlı Modal Gösterimi, Enum Serialization ve Frontend Map Sözleşmesi.
**Basit Açıklama:** Önceden frontend, "Create Ticket" sayfasında ayrı ayrı /catalog/categories, /projects, /catalog/types vb. endpoint'leri çağırıyordu. Bu hem performans kaybına hem de yanlış route çağrılarında (örneğin /types yerine /ticket-types olması gerekirken 404 dönmesi) hatalara neden oluyordu. Backend tarafına tüm referans verilerini tek seferde dönen bir `GET /api/lookup` endpoint'i eklenerek bu sorun çözüldü (Payload birleştirildi).
Modal yapılarında ise, frontend kodunda event handler'ların çalışma sırası kritik rol oynar. Vanilla JS'de modal açma fonksiyonu `style.display = 'block'` olarak geçersiz kılındığında, altta yatan CSS `.modal-overlay { opacity: 0 }` kuralı nedeniyle modal görünmez olarak kalıyordu (ölü buton hissi). Bunu çözmek için `ui.js`'den global `openModal` ve `closeModal` fonksiyonları içeri aktarılıp kullanıldı.
Son olarak, .NET backend tarafındaki C# Enum tipleri (örn. `FieldType.Text = 0`), JSON'a çevrilirken (Serialization) ya integer (`0`) ya da string (`"Text"`) olarak döner. Frontend bu değere göre CSS rozeti (badge) veya metin eşleştirirken sadece integer'a göre map yaparsa string geldiğinde "UNDEFINED" gösterir. Frontend map sözleşmesi hem sayısal ("0") hem de metinsel ("Text") anahtarları kapsayacak şekilde genişletildi.
**Projede Nerede:** `LookupController.cs`, `ticket-create.html`, `admin-fields.html`, `rules.html`, `webhooks.html`.
**Mentor Sorarsa Cevabın:** "Sistemdeki 404 ve çalışmayan buton hatalarını çözerken mimari dayanıklılığı (resilience) artırdım. Ticket oluştururken atılan 4 ayrı HTTP isteğini, backend'e yeni bir '/api/lookup' endpoint'i ekleyerek teke indirdim (Network Optimizasyonu). Modal'ların açılmama sorunu, global ui.js'deki class-based (active) açılış mantığının yerel sayfalarda style.display ile ezilmesinden kaynaklanıyordu; modül pattern'i ile bağları onardım. Enum map yapısını ise, backend serialization ayarları değişse bile (int veya string) frontend çökmesin diye iki yönlü (Two-Way Map) hale getirdim."

### Hata ve Çözüm: Status 400 ve Workflow Transition Eksikliği
- **Sorun:** Ticket detay veya Kanban üzerinden statü geçişlerinde API `400 Bad Request` veya `InvalidOperationException` dönüyordu.
- **Teşhis:** Model binding `int` tipinde doğru çalışıyordu ancak `DataSeeder` içinde hiçbir `WorkflowTransition` kaydı oluşturulmamıştı. Veritabanı boş olduğu için TicketService geçişi reddediyordu.
- **Çözüm:** `DataSeeder.cs` içine varsayılan (Default Global) bir Workflow eklendi ve Açık -> Devam Ediyor gibi temel geçiş kuralları tohumlandı. State-machine UX sağlamak için de `GET /api/tickets/{id}/allowed-transitions` uç noktası eklendi.

### Hata ve Çözüm: Ölü Butonlar ve ESM Module Kapsülü
- **Sorun:** `webhooks.html` ve `rules.html` sayfalarında modalları açan butonlar çalışmıyordu.
- **Teşhis:** `<script type="module">` (ESM) kullanıldığında, tanımlanan fonksiyonlar `window` objesine atanmadıkça global scope'ta görünmez. Dahası, `onclick="showCreateModal()"` inline event handler'ları ESM ile senkronize değildir.
- **Çözüm:** Tüm inline `onclick` handler'ları kaldırılarak element ID'leri üzerinden `addEventListener` kullanımı standartlaştırıldı.

## EF Core Include ve Navigation Property Kısıtlamaları (Faz 14)
- **Problem:** Dashboard üzerinde sayım (`CountAsync`) sorgularında `t => t.Status != null` ve `!t.Status.IsClosedStatus` kullanılmasına rağmen sonuçların hep 0 (sıfır) dönmesi.
- **Teşhis:** EF Core 3.0 ve sonrasında *Client-Side Evaluation* kısıtlanmıştır. Eğer `query` nesnesinde `Include(t => t.Status)` yoksa, `t.Status` property'sine Navigation (erişim) sırasında ya `null` değerlendirilir ve sayım boş döner ya da SQL çevirisinde beklenmedik INNER JOIN'ler oluşturarak filtreyi daraltır. 
- **Çözüm:** Tüm navigasyon property'leri (Status, Priority, Project vb.) ana base sorguya `.Include()` ile eklenerek hem bellek içi sayımların hem de ilişkisel veritabanı filtrelerinin doğru işlemesi sağlandı.

## EF Core ve Claim Yönetimi (Dashboard Bug)
- `User.FindFirst("UserId")` gibi custom claim anahtarları ararken, JWT üreten tarafın `JwtRegisteredClaimNames.Sub` ("sub") kullanıp kullanmadığına dikkat edilmeli. ASP.NET Core MVC, varsayılan olarak "sub" değerini `ClaimTypes.NameIdentifier` ile eşleştirir. Bu değer yanlış arandığında, ID varsayılan olarak 0'a düşer ve yetki hesaplamaları/veri filtrelemeleri sessizce bozulur.
- EF Core `.CountAsync()` metodu, performans optimizasyonu gereği `.Include()` ile bağlanan One-To-Many tablolarını (sonucu değiştirmeyeceği için) yoksayar. Dashboard ticket sayılarındaki sıfır hatası Include'lardan değil, RequestUserId=0 filtrelemesinden kaynaklıydı.

## HCI (Human-Computer Interaction) Temelleri ve Uygulamaları
- **Hiyerarşi ve F-Pattern:** Dashboard tasarımlarında verilerin (KPI'ların) en üstte tek bir satır (veya ızgara) halinde, sola veya F-Pattern şeklinde dizilmesi, bilişsel yükü azaltır. KPI'ları okuyan kullanıcı, sonrasında karmaşık görsellere (grafiklere) daha kolay odaklanır.
- **Grafik Boyutlandırma:** Canvas öğeleri ekranın aşırı büyük bölümünü kaplamamalıdır (`maintainAspectRatio: false` ve belirli bir `height` ile sınırlanmalıdır, örn. 260px). Donut grafikleri için cutout oranları (örn. %60-70) denge sağlamak için idealdir.
- **ID Gösterme Kuralı:** Kullanıcı arayüzlerinde son kullanıcıya ham veritabanı ID'leri gösterilmemelidir. Bunun yerine "Lookup Cache" yapılarıyla ID'ler eşleştirilerek gerçek isimler (Name, Title) sunulmalıdır.
- **State-Machine Tamamlanmışlığı:** İş akışlarında "ölü noktalardan" kaçınmak için (örneğin Resolved olan bir talebin geri alınamaması) tersine mühendislik yapılarak (Reopen) olası tüm durumların bir döngüsü kurulmalıdır. ITSM sistemlerinde Reopen sadece In Progress veya Open'a değil, ihtiyaca göre Pending'e bile geçebilmelidir.
