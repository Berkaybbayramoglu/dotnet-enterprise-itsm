# ITSM Projesi Öğrenme ve Geliştirme Notları

## Faz 8: Dashboard, Raporlama, Arama & Filtreleme, Knowledge Base
**Kavram:** Entity Framework Core In-Memory Testleri ve `IQueryable` Davranış Farklılıkları
**Basit Açıklama:** Unit testlerde kullanılan In-Memory provider, SQL'e dönüştürülen LINQ sorgularını (örneğin `.ToLower().Contains()`) client-side (bellekte) çalıştırır. Eğer veritabanında "required" (zorunlu) ilişkiler tanımlandıysa (örneğin foreign key olan bir alan nullable değilse), EF Core bu ilişkiyi `INNER JOIN` olarak algılar. Test verisi oluştururken ilişkili entity'leri (Category, Type, Priority) DB'ye eklemezseniz, In-Memory testlerde dahi `Include` veya Navigation Property sorguları (INNER JOIN nedeniyle) ana kaydı getirmez ve testler gizlice başarısız olur.
**Projede Nerede:** `ReportServiceTests.cs` (ExportTicketsToCsvAsync) ve `TicketService.cs` (SearchTicketsAsync)
**Mentor Sorarsa Cevabın:** "Raporlama servislerini test ederken In-Memory veritabanının required (zorunlu) foreign key'ler için INNER JOIN mantığında çalıştığını fark ettim. Test ortamında Ticket oluştururken Category, Type, Priority gibi zorunlu ilişkili tabloları mock olarak doldurmadığımız için `Include` yapıldığında kayıtlar eşleşmiyor ve filtreye takılıyordu. Test verilerini (Category, Type, vb.) context'e ekleyerek bu sorunu çözdüm ve `NullReferenceException`'ları engelledim. Ayrıca frontend tarafında API entegrasyonu için Fetch API kullanarak `api.js` wrapper class'ı oluşturdum."


## Faz 8: Frontend A11y & Readability (WCAG, SonarQube)
**Kavram:** Web Accessibility (a11y), WCAG Temelleri, Semantik Butonlar ve Klavye Navigasyonu
**Basit Açıklama:** Ön yüz geliştirmelerinde tıklanabilir öğeler için (aksiyon veya JavaScript fonksiyonu çağıranlar) `<a href="#">` veya `onclick` event'ine sahip `<span>`/`<div>` gibi non-native (semantik olmayan) etiketler kullanmak erişilebilirliği ve ekran okuyucu (screen reader) deneyimini bozar. Ekran okuyucular anchor etiketlerini sayfa değişimi veya içi boş link olarak okurken, native `<button>` elementlerini doğrudan "Düğme" olarak tanır ve Space/Enter tuşlarıyla yerleşik (built-in) klavye olaylarını (keydown/keyup) yönetir. Input elementleri her zaman `<label for="id">` veya `aria-label` ile birleştirilmeli, boş başlıklar (`<h2></h2>`) DOM'da bulunmamalıdır. Ayrıca modern JavaScript'te global regex (`/g`) ile `String#replace` kullanmak yerine `String#replaceAll` kullanmak kodun okunabilirliğini artırır.
**Projede Nerede:** `wwwroot` altındaki tüm HTML dosyaları (`tickets.html`, `kb.html`, `dashboard.html`) ve `api.js` (`escapeHtml` regex kullanımı vb.)
**Mentor Sorarsa Cevabın:** "Frontend sayfalarımızda aksiyon gerçekleştiren (örneğin Logout yapan) HTML öğelerini `<a href="#">` yerine CSS ile şekillendirilmiş semantik `<button type="button">` elementleriyle değiştirdim. Böylece ekran okuyuculara ve sadece klavye kullanan kişilere (tab navigation) tam destek sağladık. Form elemanlarında erişilebilirlik (aria-label) geliştirmeleri yaptım ve JavaScript kodlarımızdaki karmaşık regex değiş tokuşlarını modern `replaceAll` metoduna geçirerek 'Code Smell' hatalarını temizledim."

## Faz 8: Konfigürasyon Senkronizasyonu (Single Source of Truth)
**Kavram:** Config Drift (Yapılandırma Kayması), Single Source of Truth (Tek Kaynak Doğruluğu) ve Port Sözleşmeleri
**Basit Açıklama:** Büyük projelerde veritabanı bağlantı adresi (connection string) veya API URL'i gibi kritik yapılandırmalar birden fazla yerde hardcode edilirse, zamanla birisi güncellendiğinde diğeri unutulur; buna *Config Drift* denir. `ItsToolDbContextFactory`'nin design-time connection string'i manuel yazıldığında API tarafındaki `appsettings.json`'dan farklı kalabilir. Bu yüzden tüm veriler tek bir kaynaktan (`appsettings.json`) beslenmelidir (Single Source of Truth). Ayrıca Web projelerinin Backend API'ye istek yaparken kullandığı port, Backend'in `launchSettings.json` içindeki `applicationUrl` ayarıyla ve `appsettings.json` içindeki `Cors:AllowedOrigins` listesiyle kesinlikle eşleşmelidir.
**Projede Nerede:** `ItsToolDbContextFactory.cs`, `api.js`, API `appsettings.json` ve `launchSettings.json`
**Mentor Sorarsa Cevabın:** "Çalışma zamanında connection string uyuşmazlığından ve port sorunlarından kaçınmak için `ItsToolDbContextFactory` sınıfını refactor ettim; artık connection string'i hardcoded olarak değil, dinamik olarak `ItsTool.API` içindeki `appsettings.json` dosyasından okuyor. Ayrıca frontend API istek URL'ini API'nin `launchSettings.json` portuyla tam hizaladım ve CORS izinlerini doğruladım."

## Faz 8: ASP.NET Core Static Files Middleware & Routing
**Kavram:** Middleware Pipeline, `UseStaticFiles`, `UseDefaultFiles` ve Routing (Yönlendirme)
**Basit Açıklama:** ASP.NET Core uygulamasında `wwwroot` altındaki HTML/CSS/JS dosyalarını dışarı sunmak için HTTP pipeline'ında `app.UseStaticFiles()` çağırmak zorunludur. Ayrıca `http://localhost:5139/` gibi kök dizin isteklerinde otomatik olarak `index.html` sayfasının servis edilmesi için `app.UseDefaultFiles()` eklenmelidir. Bu iki middleware'in *sıralaması* çok önemlidir; `UseDefaultFiles`, URL'i `index.html` olarak rewrite (yeniden yazma) işlemi yapar ancak dosyayı servis edemez, bu yüzden **mutlaka** `UseStaticFiles`'dan önce çağrılmalıdır. Aksi halde `MapGet("/")` gibi minimal API route'ları (örneğin "Hello World" placeholder'ı) isteği yakalar ve statik dosyaların gösterilmesini engeller.
**Projede Nerede:** `ItsTool.Web/Program.cs`
**Mentor Sorarsa Cevabın:** "Web projemizde `wwwroot` içindeki frontend kodlarımızın tarayıcıdan açılmamasının sebebi, ASP.NET Core'un varsayılan olarak statik dosya sunumuna kapalı olması ve kök dizinin API endpoint'ine (Hello World) yönlendirilmiş olmasıydı. `Program.cs` dosyasına, URL'i `index.html`'e yönlendirmesi için `app.UseDefaultFiles()` ve ardından bu dosyayı fiziksel olarak sunması için `app.UseStaticFiles()` middleware'lerini doğru sırayla ekleyerek sorunu çözdüm."

## Faz 8: HTML5 Validation ve Backend Login Sözleşmesi
**Kavram:** Client-Side Validation vs Backend Sözleşmesi, "Username or Email" Pattern'i
**Basit Açıklama:** HTML5'teki `type="email"` özelliği, form submit edilmeden önce tarayıcının '@' işareti gibi email formatlarını zorlamasını sağlar (Client-Side Validation). Eğer backend sistemi (AuthService) kullanıcının hem "Username" (örn: admin) hem de "Email" ile giriş yapmasına izin verecek şekilde tasarlandıysa, frontend'deki katı `type="email"` kısıtlaması, doğru bir Username girildiğinde bile isteğin API'ye gitmesini engeller. Bu uyuşmazlığı çözmek için frontend'de input `type="text"` (veya tel, vs.) olarak esnetilir ve `autocomplete="username"` ile tarayıcıya ipucu verilir. Backend'de ise veritabanı sorgusu `Username == input OR Email == input` şeklinde genişletilir.
**Projede Nerede:** `login.html` ve `AuthService.cs` (`LoginAsync` metodu).
**Mentor Sorarsa Cevabın:** "Login formunda sadece e-posta değil, 'admin' gibi kullanıcı adlarıyla da giriş yapılabilmesi gerekiyordu. Ancak HTML'deki `type="email"` kısıtlaması yüzünden 'admin' yazınca tarayıcı '@' beklediği için formu göndermiyordu. HTML'deki input tipini `text` olarak güncelledim ve backend `AuthService`'i hem Username hem de Email ile eşleşme (case-insensitive) yapacak şekilde refactor ettim."

## Faz 8: Dashboard Frontend-Backend Veri Kontratı
**Kavram:** Frontend-Backend Sözleşmesi (Contract), DTO Naming Conventions ve Defensive Rendering
**Basit Açıklama:** Backend tarafında C# ile oluşturulan DTO'lardaki property isimleri (örneğin `SlaBreachedTickets`), JSON olarak serialize edildiğinde varsayılan olarak camelCase yapısına (`slaBreachedTickets`) bürünür. Frontend JavaScript kodu, backend API'den gelen veriyi render ederken hatalı özellik (property) isimleri kullanırsa (örneğin `slaBreachedCount`) değer `undefined` döner ve HTML içinde hatalı görünür. JavaScript tarafında veriyi ekrana basarken `?? 0` (Nullish Coalescing Operator) gibi tekniklerle varsayılan (fallback) değerler vermek, veri gelmediğinde arayüzün bozulmasını engeller (Defensive Rendering).
**Projede Nerede:** `DashboardOverviewDto.cs`, `dashboard.html`
**Mentor Sorarsa Cevabın:** "Dashboard arayüzünde bazı metriklerin 'undefined' yazdığını tespit ettik. İncelediğimde C# tarafındaki DTO'nun (DashboardOverviewDto) `SlaBreachedTickets` isimli property döndürdüğünü, ancak JS tarafında bunun `slaBreachedCount` olarak okunduğunu gördüm. Tek doğru kaynağın (Single Source of Truth) backend DTO'su olması prensibiyle JS tarafını DTO isimlerine uyacak şekilde (camelCase haliyle) güncelledim. Ayrıca verilerin `null` gelme ihtimaline karşı defensive rendering uygulayarak `(deger ?? 0)` fallback yapısını ekledim."

## Faz 9: Gelişmiş Dinamik Yapılandırma & Rules Engine Deseni
**Kavram:** Rules Engine (Condition-Action) Deseni, Config-Driven Form Render, Saved Filter Serialization, Event-Driven Notification Fan-out.
**Basit Açıklama:** Gelişmiş dinamik konfigürasyonlarda (örn. Bilet Atama Kuralları) sisteme hardcode edilmiş bir atama mantığı yazmak yerine, kuralların bir tabloda (AssignmentRules) tutulup çalışma zamanında (Runtime) değerlendirilmesi *Rules Engine* desenidir. Böylece kodu değiştirmeden yeni kurallar eklenebilir. Benzer şekilde, bilet formları da `FormFieldPlacement` üzerinden "Config-Driven" olarak JSON aracılığıyla render edilir. Event-Driven bildirim üretiminde ise `NotificationDispatcher`, bir olay (örn: ticket.created) gerçekleştiğinde abone olan kuralları tarayarak "Fan-out" (çoğaltma) yapar ve kişilere özel bildirim yaratır; aynı kişiye aynı olay için bir daha bildirim atılmasını engellemek de (Duplicate Prevention) önemli bir tasarım kararıdır.
**Projede Nerede:** `AssignmentEngine.cs`, `NotificationDispatcher.cs`, `SavedFilterController.cs`, `ticket-create.html` ve `api.js`.
**Mentor Sorarsa Cevabın:** "Uygulamamızı tamamen 'Configuration-Driven' yapmak için, bilet açıldığında kimlere atanacağına karar veren bir *Assignment Rules Engine* yazdım ve bilet akışına entegre ettim. Ayrıca *Notification Dispatcher* pattern'i uygulayarak biletteki tüm önemli state değişikliklerini (created, assigned, comment_added) dinleyen ve aktif kurallara göre çoklu kişilere spam/duplicate olmadan bildirim atan bir mekanizma kurdum. Kullanıcıların arama filtrelerini kaydetmeleri için JSON serialization tekniğini (SavedFilter) kullandım ve son olarak bilet formlarının tamamen konfigürasyon tabanlı olarak dinamik şekilde render edildiği UI altyapısını oluşturdum."

## Faz 10: Bonus Özellikler Dalgası (Audit Log, Kanban, CSAT)
**Kavram:** Audit Logging, Kanban (Drag-and-Drop) State Management, Customer Satisfaction (CSAT) Feedback Loop.
**Basit Açıklama:** Gelişmiş sistemlerde "Kim, neyi, ne zaman değiştirdi?" sorusunu yanıtlamak için *Audit Log* pattern'i kullanılır. Kanban board ise görsel durum (state) yönetimi sağlar; drag-and-drop ile sürükleyip bırakılan bir bilet aslında arka planda bir "durum geçişi (state transition)" API isteğine dönüşür. CSAT ise sistemdeki kaliteyi ölçmek için bir "Geri Bildirim Döngüsü (Feedback Loop)" oluşturur; olay (bilet kapatılması) anket formunu tetikler ve alınan veriler dashboard'da toplanarak kalite metriği sunar.
**Projede Nerede:** `AuditLogController.cs`, `audit-log.html`, `kanban.html`, `survey.html`, `TicketService.cs`.
**Mentor Sorarsa Cevabın:** "Uygulamanın kullanım kolaylığını ve şeffaflığını artırmak için bonus özellikler geliştirdim. *Audit Log* ekranı ile TicketHistory verisini filtreleyip yöneticilere (audit.view yetkililerine) detaylı bir log ekranı sundum. Biletlerin görsel olarak yönetilebilmesi için HTML5 drag-and-drop kullanarak bir *Kanban Board* yazdım; burada kartlar sürüklendiğinde sistemdeki statü değiştirme iş mantığını yeniden kullandım. Ayrıca kalite ölçümü için *CSAT (Müşteri Memnuniyeti)* döngüsü oluşturdum; bilet kapatıldığında kullanıcıya anket bildirimi gidiyor ve doldurulan anket puanları doğrudan dashboard metriklerine yansıyor."
